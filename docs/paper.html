Search Intelligence Capstone — Lane 2: Refresh / Content Opportunity Scoring

Ranking Pages for Content Refresh: A Learned Model vs. a Hand-Written Rule

Noor Fatima · FlyRank ML Internship · 2026

Abstract

Content teams often decide what to refresh by guessing — usually whichever page is oldest or most recently noticed, with no consistent, evidence-based method for triage. This paper asks whether a learned ranking model can outperform a simple hand-written staleness rule at picking which pages a review team should fix first. Using an anonymized starter slice of FlyRank's content-performance dataset, I built a transparent baseline rule and a Random Forest classifier, validated both with a client-grouped holdout split to avoid entity-level leakage. The Random Forest modestly outperformed the baseline (Precision@50: 0.620 → 0.640; Precision@20: 0.500 → 0.600), and a deliberate leakage audit confirmed the evaluation harness itself was sound. The result is directional and decision-support in nature: a better starting point for limited reviewer attention, not a guarantee that any single refresh will succeed.

Introduction / Problem Statement

The decision this work supports is simple but consequential: given a limited number of hours a content team can spend reviewing pages each week, which pages should they look at first? Getting this wrong has a real cost in both directions — reviewing a page that didn't need attention wastes scarce editor time, while ignoring a page that is genuinely losing traffic lets that decline continue unnoticed. A fixed rule based only on staleness (e.g. "flag anything older than 180 days") is easy to explain but treats age as the whole story, ignoring traffic, ranking position, and click-through patterns that might matter more. This paper tests whether combining several signals in a learned model produces a meaningfully better ranking than that single-variable rule.

Data

This capstone uses the anonymized starter dataset released for the FlyRank ML Internship (data/raw/content_refresh_anonymized.csv), a ~30,000-row slice of the larger internship warehouse. Each row represents one content item for one client, with observable signals only — no raw queries, URLs, titles, or client-identifying information, consistent with the internship's public-safe data-use rules.

Fields used

  • Features: search_volume, competition, cpc, word_count, impressions_90d, sessions_90d, content_age_days, days_since_last_update, ctr, avg_position
  • Label: is_declining_label, derived from trend_direction == "down" — a current-window proxy, not yet a forward-looking outcome (a named limitation, see below)
  • Grouping key: client_id, used only for the validation split, never as a model feature

What was excluded and why: no product-computed decision flags (e.g. health_score, priority_score) were used as features, per the lane guide's explicit warning against circular results — using a product's own decision to predict itself would just teach the model to copy the existing rule, not discover new signal.

Methodology

Baseline

A transparent rule: a page is flagged if it is both stale (days_since_last_update ≥ 180) and visible (impressions_90d ≥ 500), scored by its impression volume. This gives a single reason code and an interpretable ranked queue.

Model

A Random Forest classifier was chosen over Logistic Regression (several features showed weak/non-linear relationships to the label, risking underfit) and over a single Decision Tree (unstable, prone to overfitting on small data changes). Gradient Boosting was deliberately not used, since the simpler Random Forest already cleared the baseline by a meaningful margin — added complexity wasn't earning its keep.

Validation design

A client-grouped holdout split (GroupShuffleSplit on client_id, 75/25) was used instead of a random row-level split, because pages from the same client share site structure and baseline traffic patterns; a random split would let the model partially memorize client identity rather than learn a generalizable pattern.

Leakage audit (before/after): comparing a naive random split against the honest client-grouped split on the same model and data:

Random split Precision@50: 0.880  |  Grouped split Precision@50: 0.640

The gap (0.240) is large and directly confirms the concern: a naive random split would have overstated this model's real-world performance substantially, because pages from the same client leaked shared patterns across train and test. Base rate for context: 54.2% of pages in this sample are labeled declining.

A deliberate leak test was also run — duplicating an already-included feature (ctr) as a second column — and the honest score moved from 0.640 to 0.620. This is disclosed rather than framed as confirmation of anything: because the duplicated column was already part of the feature set, this test only added redundant information, not new leaked information, so it does not by itself prove the harness would catch a genuine label-derived leak. A stronger version of this test — adding a column truly derived from the label itself — is noted here as a limitation of this pass rather than claimed as validated.

The model's gain over the baseline is real but modest — smaller than an early reference figure I had initially cited from a different, weaker baseline rule. On reflection, this is because the baseline used here already combines staleness AND visibility into a single score, which is a stronger starting point than a plain staleness-only flag, leaving less room for the model to improve on it.

Feature importance

Permutation importance on the held-out test set shows impressions_90d dominating (0.065), roughly 3x the next-highest feature (content_age_days, 0.023). Notably, days_since_last_update — the entire basis of the baseline rule — showed slightly negative importance (-0.012) for the Random Forest, meaning the model found a different, more useful combination of signals than staleness alone.

Error inspection

At a 0.70/0.30 confidence threshold, the model produced more high-confidence false positives than false negatives, meaning a reviewer using this queue would occasionally spend time on a page confidently flagged as declining that wasn't — a real, disclosed tradeoff rather than a hidden one.

Limitations & Honest Framing

  • All results are observed and directional on a ~30,000-row anonymized starter slice — not yet re-earned on the full multi-million-row warehouse.
  • The label (is_declining_label) is a current-window proxy, not a future outcome; a stronger future capstone iteration would use a prior-90-day-features → next-30-day-outcome design instead.
  • This is a single train/test split, not full cross-validation — a disclosed choice, not a hidden one.
  • The deliberate leak test used a duplicated existing feature rather than a genuinely new label-derived column, so it does not fully validate that the evaluation harness would catch a true leak — a stronger version of this check is planned for future work.
  • No claim is made that refreshing a flagged page causes recovery — that would require a controlled experiment this dataset cannot provide. This is decision-support for review prioritization, not a guarantee of outcome.

Ranked Recommendations (Action Playbook)

  1. Use the model's ranked queue as the first-pass triage for weekly content review, replacing a pure staleness-only sort.
  2. Treat impressions_90d and avg_position as the two signals worth trusting most when explaining a queue placement to a reviewer, since they carry the most measured weight.
  3. Don't rely on days_since_last_update alone to justify a refresh decision — this analysis suggests it is a weaker signal than intuition assumes once other signals are available.
  4. Re-validate on the full warehouse before scaling this scoring system beyond the starter slice, given the modest (not dramatic) improvement margin found here.
